# ADR 0001: Imperative Three.js Scene Engine Instead of React Three Fiber (R3F)

- **Status:** Proposed in Redevelopment Plan (Deliverable 3 & 4) / Pending Implementation Validation in Phase 4
- **Date:** October 30, 2026
- **Source Plan Reference:** `concepful-redevelopment-plan.md` Deliverable 3 (line 173), Deliverable 4 (lines 201–203, 217), and Deliverable 8 (line 362)

---

## Context

The original **Concepful Mech Builder** prototype (`reference/Concepful_Mech_Builder.html`) is an imperative WebGL application using Three.js r128. It renders a single tightly-coupled procedural 3D world comprising over 40 custom low-poly mecha models, complex procedural geometries, custom toon shaders, ink line outlines, camera target easing, and dynamic party formation layouts.

In `concepful-redevelopment-plan.md` (Deliverable 3), the architectural choice between **React Three Fiber (R3F)** and a **framework-agnostic imperative Three.js engine** encapsulated behind a single client React component (`SceneHost.tsx`) was evaluated.

---

## Proposed Decision

As proposed in Deliverables 3 and 4 of the redevelopment plan, the project plans to implement a **framework-agnostic imperative Three.js engine** in `src/scene/` rather than using React Three Fiber.

Under this proposed architecture:
`SceneHost.tsx` will act as a thin client wrapper that mounts the imperative engine to an HTML `<canvas>` element via a `useEffect` lifecycle hook, provides a read-only state snapshot, and triggers the engine's `dispose()` method on unmount.

_(Note: No application scene code or dependencies have been implemented yet; this architecture will be validated upon implementing Phase 4)._

---

## Rationale (from Redevelopment Plan)

1. **Direct Porting of Procedural Generation:**
   The original prototype contains ~12,850 lines of imperative procedural mesh construction, custom geometry manipulation, and mathematical matrix calculations. Porting these directly to an imperative TypeScript module allows function-by-function verification against the source code without rewriting procedural loops into JSX declarations.
2. **Reconciliation Overhead & Performance:**
   R3F introduces a custom React reconciler that runs overhead on state changes. In this application, scene updates are driven continuously at 60 FPS by a single `requestAnimationFrame` loop that coordinates scroll targets and camera positions. Bypassing the React reconciler avoids unnecessary VDOM diffing.
3. **Strict Memory Management & Disposal:**
   Three.js applications in single-page apps can easily leak WebGL contexts, geometries, and textures across navigation or hot reloads. Keeping scene lifecycle, resource disposal, and WebGL context loss handling inside an explicit `dispose()` method in `src/scene/engine.ts` makes memory management straightforward and testable (e.g., verifying 20 mount/unmount cycles).
4. **React 19 Compatibility:**
   At the time of implementation, React 19 is used. Decoupling the 3D engine from React component lifecycles eliminates third-party reconciler version conflicts.

---

## Consequences & Validation Criteria

### Expected Advantages

- Direct mathematical and visual parity with prototype procedural code.
- Zero extra React reconciler dependencies or overhead.
- Total control over the render loop, visibility pauses, and reduced-motion handling.
- Full StrictMode safety through a simple `mount()` / `dispose()` contract.

### Trade-offs & Validation Requirements

- Scene entities cannot be styled or manipulated directly via standard React props; updates must pass across a lightweight state bridge (`scene/state.ts`).
- Validation in Phase 4 requires proving clean mount/unmount cycles (zero memory or context leaks after 20 cycles) and verifying that camera and layout easing match the reference baseline.
